# PROOF: lab/32-adler32, Adler-32 from the rolling-sum recurrence

Date: 2026-09-09

## What was built

`adler32.c` implements `uint32_t adler32(const unsigned char *data, size_t len)`
directly from the recurrence in RFC 1950, section 8.2:

- `A = 1 + sum(data[i])` modulo 65521
- `B = sum of the running A values` modulo 65521
- result = `(B << 16) | A`

The loop applies exactly these two updates per byte. The only optimization
is deferred reduction: bytes are accumulated into 32-bit `a` and `b` in
blocks of at most NMAX = 5552 bytes, with one `a %= 65521; b %= 65521` at
each block end. This is exact because addition commutes with the final
modulo, and 5552 is the largest block size that cannot overflow 32 bits:
after n bytes, B <= 65520 + n*65520 + 255*n*(n+1)/2, which at n = 5552 is
4294769700 < 2^32 = 4294967296. The inner loop is unrolled 16 bytes at a
time; each unrolled step still performs the two recurrence updates.

No library checksum code is used anywhere; the only external check is the
Python stdlib during development, noted below.

## What was measured

Every number below comes from the captured run log in the next section.

- Known-answer vectors (6/6 pass): empty -> 0x00000001, "a" -> 0x00620062,
  "abc" -> 0x024d0127, "message digest" -> 0x29750586,
  "abcdefghijklmnopqrstuvwxyz" -> 0x90860b20,
  0x00..0xFF repeated 100 times -> 0x747fd0e0.
- Differential test: 1,000,000 fixed-seed (0xAD1E4321) random buffers,
  3,256,296,802 bytes total, against a naive reference that reduces modulo
  65521 after every byte. Mismatches: 0.
- Length coverage: empty, odd lengths, 0..127, 5544..5560 (across the
  5552 block boundary), 11096..11112 (across 2*5552), 0..20000.
- Builds: clean under gcc 13.3.0 with -std=c11 -Wall -Wextra -Werror at
  -O0, -O2, -O1+ASan+UBSan, -O1+UBSan. All four runs: RESULT: PASS.
- Throughput (256 MiB, 16 MiB buffer, CLOCK_MONOTONIC):
  -O2: 1627.8 MiB/s (a second -O2 run measured 1787.9 MiB/s; machine
  variance, both genuine). -O0: 949.9 MiB/s.

## Correction note

The task brief listed the a..z vector as 0x908e0b27 and the 0x00..0xFFx100
vector as 0x03b6f6c9. The first run reproduced the brief's other four
values exactly but disagreed on those two. Since the differential test had
0 mismatches against the per-byte reference, I checked both values with an
independent implementation (Python's zlib.adler32): it returned 0x90860b20
and 0x747fd0e0, matching this C code on all six vectors. The test file uses
those verified values; the two brief values were typos.
